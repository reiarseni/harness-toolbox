# Output templates

Skeletons, not forms: drop sections that don't apply (except the ones the
checker requires); add ones that are missing. **Headings are shown in English —
write them in the docs' language.** File names and required headings must match
[languages.md](languages.md) exactly (the checker matches them). File names
below use `en`. **Reading order = numbering** (general → specific); the
**writing order** is in `SKILL.md` Step 4.

## `README.md` — front door

```markdown
# <System> — developer documentation

<What it is, 2-3 sentences: problem solved and for whom. No marketing.>

> Generated by documake from commit `<sha>` (<date>). If the code moved a lot
> since, distrust details and trust names: paths and symbols are searchable.

## Quickstart        <FORCED: clean clone → first working result, 1–5 numbered steps>
1. `git clone <url> && cd <repo>`
2. `cd backend && <install>`          <every command states its working directory>
3. `cd backend && cp .env.example .env`  <only the values that must change>
4. `cd backend && <start>`
5. <how to see it working: URL / expected output / command that prints "ok">
Full detail: Environment and testing. If a step could not be run on a clean
clone, mark it `[UNVERIFIED]`; never invent a step.

## Start here, by goal
| I came to… | Read, in order |
|---|---|
| Make my first change here | First change (tutorial) |
| Know what this repo is made of and where it sits | Stack and repository → Structure |
| Understand the system from scratch | Overview → Code map → Architecture |
| Understand the data | Data |
| Fix a bug in <area> | Code map → <area> card → Pitfalls |
| Add a feature | Change recipes → affected module card |
| Run it locally | Environment and testing |
| Decode a strange word | Glossary |

## Index        <every doc, one line each, linked; include the operations doc when it exists>
## Not covered here   <and where to look instead>
```

**Link text is the destination's own name.** `[Flows](07-flows/checkout.md)`
lies: it reads like the whole group and lands on one page. Either link each page
by its name, or make the group a bold label and list its pages under it. The
checker flags the lie.

**Mind the `../`.** Cards and flows live in a subfolder, so a link from one of
them to a top-level doc is `../09-change-recipes.md`. The checker reports the
missing `../` as a broken link.

## `00-first-change.md` — the way in (tutorial)

The only doc written in the second person, and the only one whose steps you
**run** before writing them down. Goal: someone who has never seen the repo
changes something real and sees the change. Not a tour of the architecture —
one small, genuinely useful change, end to end.

Pick the change from the recipes: the shortest one that crosses at least one
boundary (an API response field the UI shows, a validation rule with a test).
Avoid anything needing credentials, external services or a GPU.

```markdown
# Your first change

<One sentence: what you will have changed and seen by the end, and the rough
time. "In about 20 minutes you will add a field to the employee response and
see it in the panel.">

## Before you start
<What must already work: the quickstart, done. Link it. One command that proves
it, with its expected output.>

## The change
1. <One action per step: file to open, what to write, why that file.>
   `path` · `Symbol`
2. …
<Each step is checkable. If a step can fail in a common way, say how it looks
and what to do — right there, not in a pitfalls section.>

## Check it works
<The command and the expected output, and where in the UI/API it shows. The
reader must be able to tell success from failure without asking anyone.>

## Undo it
<How to leave the repo as it was: `git checkout -- <paths>`, drop the migration…>

## What to read next
<2-3 links, by what they came for. Send them to the code map and the recipes.>
```

**Executed, not drafted.** Run every step in a clean clone before writing it.
A step you could not run is either dropped or marked `[UNVERIFIED]` with what
blocked it — and if most of it is unverified, say so in the coverage file and
set `"tutorial": false` rather than ship a tutorial that fails.

## `09-change-recipes.md`

**The only place procedures live.** Cards and flows link here; they never carry
their own numbered steps. One recipe per recurrent change, including the ones
that stay inside a single module — if a card would have listed steps, they
belong here under a recipe the card links.

Pulling them together is what exposes the drift: two half-recipes for one change
(the server half in one card, the client half in another) merge into one, and a
recipe that restates another under a different name disappears. Expect that, and
merge rather than paste.

Past ~10 recipes, group them with `##` per area and `###` per recipe, and open
with a plain-text index — **not links**: anchors break across wiki and site
targets. Cards name the recipe in quotes and link the file.

```markdown
# Change recipes
The most recurrent changes, with **every** touch point. A recipe missing a
step is a bug in these docs.

## <Add an endpoint / command / entity / field / provider…>
**Touches:** <areas>
1. `path` — <what and why>
**Verify:** `cd backend && <test command>`
**Don't forget:** <the step everyone forgets>

Working directory: in a multi-app repo or monorepo **every command states where
it runs** (`cd backend && …`, `cd frontend && …`, or "(from `backend/`)" in the
step). Readers run commands from the root out of habit; the checker warns when
a command has no directory. In a single-project repo, plain commands are fine.
```

## `13-operations-and-data.md` (forced when there is evidence)

Written from the **Operations evidence** block of `repo.py`, then verified.
Required when the repo has compose/Dockerfiles, git-ignored folders that hold
data, storage/backup/observability references or an observability service. Skip only
with `"operations": false` in `_meta/documake.json` plus the reason in coverage.
Everything documented here is what **is not in git or runs around the code**:
what you must back up, and where to look when it breaks.

```markdown
# Operations and data

## Docker             <required when compose/Dockerfiles exist>
| Service | Image / build | Ports | Volumes | Depends on | Role |
Which compose file is for dev / prod, how to start, stop and rebuild, where
images are built (CI job) and which registry holds them.

## Data outside git
Everything the app writes at runtime that git ignores. One row per folder or
volume — **with the reason**:
| Path / volume | What is stored | Written by | Why it is outside git | In backup? |
|---|---|---|---|---|
| `backend/uploads/` | Photos users attach to a ticket | `UploadService.save` | User data, unbounded size | Yes — with the DB dump |
Bind mounts and named volumes (compose), upload/media folders, local databases,
generated files that cannot be rebuilt. **Evaluate each ignored folder before
deciding** — the name alone proves nothing: (1) who writes into it (grep the
code), (2) can the app rebuild it from git plus a command, (3) would deleting it
lose something a user or admin created. Cannot rebuild → row in the table and it
goes in the backup. Can rebuild → one line saying it is disposable and why.
Folders the checker flags with a *strong* signal (uploads, media, DB volumes,
ignored bind mounts) must appear here; *weak* ones (`data/`, `exports/`…) get a
warning until decided. To silence a folder for good, record the decision in
`_meta/documake.json`: `"operations_ignore": [{"path": "data/cache/", "reason": "Rebuilt by `make cache`"}]`
(a reason is required).

## Backups
| What | Destination (disk path / S3 bucket) | How | Frequency | Retention | Restore |
|---|---|---|---|---|---|
| Database | … | `<script/cron/CI job>` | … | … | `<command>` |
| Uploaded files | … | … | … | … | … |
Database **and** user files, together. Evidence first (scripts, cron, CI jobs,
compose services, S3 variables); backups are often configured on the server or
in an infra repo, so what the code does not show is `[ASK: who runs it and
where does it go?]`, never invented. Restore is part of the backup: if nobody
knows how to restore, say so.

## Logs and observability
| Signal | Where to look | How to read it |
|---|---|---|
| App logs | `docker compose logs -f <svc>` / file / stdout | level via `LOG_LEVEL` |
| Errors | Sentry project / other | `SENTRY_DSN` |
| Metrics / traces | … | … |
Log location per environment, rotation, and the error/metrics/tracing tools in
use. If there is none, say what was searched.
```

```json

```

when the checker detects tables.
